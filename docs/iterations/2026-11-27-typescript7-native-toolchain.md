# TypeScript 7 build ownership and explicit API compatibility

## Decision and scope

The 2026-11-27 completion request for #793 asks to use the current TypeScript release and avoid idle CI waits; merge remains conditional on the complete final-head qualification below. The implementation uses the upstream-supported side-by-side installation: native TypeScript **7.0.2** owns project compilation and type checking, while a separately identified compatibility package supplies the JavaScript Compiler API required by existing tools.

This is an explicit transition profile. It does **not** complete the earlier target that every embedded compiler/parser run TypeScript >=7.0.2. That broader target remains future tooling work; it must not be described as fulfilled by a native preflight or by the compatibility alias. The earlier T0 document is retained as historical evidence, with this decision linked from its status.

| Responsibility | Installed identity |
| --- | --- |
| Build, project type checking, normal `tsc` CLI | `@typescript/native` alias to `typescript@7.0.2` |
| JavaScript Compiler API for Jest, ts-node, typed ESLint and AST tools | `typescript` alias to `@typescript/typescript6@6.0.2` |
| Underlying compatibility implementation | Locked `@typescript/old` alias to `typescript@6.0.3` |
| Jest transformation integration | `ts-jest@29.4.15`, including upstream alias support introduced in 29.4.12 |

The wrapper version and the underlying API version are different. Registry inspection rejected the nonexistent `@typescript/typescript6@6.0.3`; the published wrapper is 6.0.2. The lockfile must be generated by npm, preserving real package integrity and ordinary peer resolution.

## Why this change is needed

TypeScript 7's native compiler does not expose the former JavaScript Compiler API. Replacing the root dependency alone breaks ts-node and ts-jest at missing `sys` functions and conflicts with supported peer ranges. The existing separate-prefix TS7 workflow proves configuration and source compatibility, but it leaves the normal build on TS6.

The official [ts-jest TypeScript 7 guide](https://github.com/kulshekhar/ts-jest/blob/main/website/docs/guides/typescript-7.md) documents the two aliases and recommends native TS7 as the authoritative project type check. Microsoft's [side-by-side announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6-0) describes the compatibility package. The [ts-jest changelog](https://github.com/kulshekhar/ts-jest/blob/main/CHANGELOG.md) identifies the supported transformer release.

This scope preserves existing Nest DI, CommonJS output, declaration emit, strict compiler options, all 34 path aliases, type-aware lint and test inventory. It does not replace the existing 195 ts-node script commands or 40 Compiler API consumers with an experimental integration. API compatibility is visible in both the manifest and this record.

## Bounded implementation

1. Add exact native/compiler-API aliases and the narrowly required ts-jest update in `package.json`; regenerate `package-lock.json` with npm without `--force` or `--legacy-peer-deps`.
2. Make the existing build and new explicit typecheck command invoke the installed native compiler. Keep emitted-alias rewriting as a declared compatibility-API operation.
3. Change the existing TS7 workflow to use the locked project installation for native typecheck and build. Remove its separately installed compiler prefix.
4. Extend the existing TypeScript configuration contract with executable compiler identity, invalid-source rejection and actual Nest decorator metadata/DI checks.
5. Update the two existing compiler fixtures to compile with native TS7 and the existing HTTP-fixture build-command contract to require the new native pipeline. Preserve emitted-JavaScript/declaration alias assertions and standalone host-artifact behavior.
6. Keep the historical plan linked to this current decision and correct the documented deep compiler CLI example.

Estimate before implementation: approximately 150–300 changed code/test/config lines, plus the generated lockfile and this evidence record. Complexity **4/10**; reliability target **9/10**; confidence in the bounded design **8/10**, conditional on the checks below. These are estimates, not test results.

## Review critiques and corrections

1. **A manifest alias does not prove CLI ownership.** The nested old package also publishes a `tsc` bin. Verify the actual installed root `.bin/tsc` target and execute its `--version`; explicitly select native TS7 in build/typecheck commands.
2. **A passing typecheck does not prove working Nest output.** Compile a real decorated fixture using native TS7, inspect runtime metadata, instantiate it through Nest and close the application context. Keep this synthetic fixture out of the production source inventory.
3. **Old compiler deep imports bypass the chosen owner.** Replace the two fixture CLI entrypoints and their removed `baseUrl` options. Preserve the compatibility API dependency closure used by the alias rewriter in the host fixture, without shipping either development compiler in the final host artifact.
4. **Older transformer releases predate upstream alias support.** Update only ts-jest to the verified supported patch. Preserve the existing Jest and typed ESLint behavior instead of suppressing their diagnostics or forcing peers.
5. **Concurrent PRs modify the same architecture test command.** When integrating #783, retain its added suites and dependency-policy test together with #793's removal of the 12 obsolete Node flags. Preserve the merged November archive and X bootstrap corrections.
