# 111. Idempotency Policy

## Status

Locked for implementation blueprint.

## Research Anchors

- IETF Idempotency-Key draft: https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header
- MDN Idempotency-Key header: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Idempotency-Key
- Stripe idempotent requests: https://docs.stripe.com/api/idempotent_requests

## Decision

Idempotency is mandatory for all externally retriable commands and all internally retried jobs/events that can create side effects.

## HTTP Idempotency

Require `Idempotency-Key` for:

- create topic;
- create source binding;
- update scan policy;
- trigger backfill;
- create notification channel;
- create API key;
- billing/checkout operations;
- destructive workflows that can be retried by clients.

Policy:

- key scope is `(tenant_id, actor_id, route, idempotency_key)`;
- key must be high entropy, preferably UUID/ULID generated by client;
- store request fingerprint, status code, response body ref and expiry;
- same key + same fingerprint returns first completed result;
- same key + different fingerprint returns conflict;
- in-progress duplicate returns `409` or retryable `425/409` style domain error depending on endpoint semantics.

## Job and Event Idempotency

Internal side-effect handlers must use deterministic keys:

```text
source_fetch:{tenant}:{binding}:{cursor}
normalize:{raw_payload_ref}
summary:{tenant}:{cluster_id}:{summary_policy_version}
notify:{tenant}:{digest_id}:{channel_id}
delete:{tenant}:{data_class}:{batch_id}
```

Consumers must be safe under at-least-once delivery. Do not assume Kafka/RabbitMQ gives exactly-once business effects.

## Storage

Use Postgres for durable command idempotency records. Redis can be a fast guard, but Redis alone is not enough for irreversible side effects.

Retention:

- public command idempotency: 24 hours minimum, 7 days preferred for expensive operations;
- billing/webhook idempotency: 30 days;
- internal job dedupe: by job class, usually 7-30 days.

## Best-Fact Choice

Idempotency must be a platform primitive, not a per-handler habit. Retries are unavoidable across mobile networks, queues, providers and webhooks.
